# Timeout Strategy - Единая стратегия таймаутов

**Версия:** 2.0 (19 августа 2025)  
**Статус:** Production Ready + Sequential Processing  
**Проблема решена:** Зависание процесса на cloud.google.com и других источниках

## Обзор

До версии 3.4 система использовала множество несогласованных таймаутов, что приводило к зависаниям процесса. Самый яркий пример - зависание на cloud.google.com 18.08.2025 в 15:28:22, когда процесс не перешел к следующему источнику более 30 минут.

## Старая конфигурация (проблемная)

```python
# Несогласованные таймауты
asyncio.wait_for(timeout=30)      # monitor.py
aiohttp.ClientTimeout(total=40)   # FirecrawlClient - БОЛЬШЕ чем asyncio!
sock_connect=5                    # Лишняя детализация
sock_read=30                       # Лишняя детализация
max_retries=1                      # Недостаточно для временных сбоев
```

**Проблема**: aiohttp timeout (40s) > asyncio timeout (30s) = потенциальное зависание

## Новая конфигурация (v4.0)

### Единая стратегия таймаутов

```python
# change_tracking/monitor.py:223
asyncio.wait_for(timeout=60)      # Главный таймаут на источник

# services/firecrawl_client.py:90
aiohttp.ClientTimeout(total=55)   # HTTP таймаут МЕНЬШЕ главного

# change_tracking/monitor.py:97
max_retries=3                     # Достаточно попыток для надежности
```

### Иерархия таймаутов

```
┌─────────────────────────────────────┐
│  asyncio.wait_for (60 секунд)       │  ← Главный контроль
│  ┌─────────────────────────────┐    │
│  │  aiohttp (55 секунд)        │    │  ← HTTP уровень  
│  │  ┌───────────────────┐      │    │
│  │  │  HTTP запрос      │      │    │
│  │  └───────────────────┘      │    │
│  └─────────────────────────────┘    │
└─────────────────────────────────────┘
```

## Преимущества новой стратегии

1. **Простота**
   - Один главный таймаут (60 сек) вместо множества
   - Легко понять и настроить

2. **Надежность**
   - asyncio timeout > aiohttp timeout гарантирует отсутствие зависаний
   - 3 retry попытки для временных сбоев

3. **Предсказуемость**
   - Максимум 3 минуты на проблемный источник (3 × 60 сек)
   - Понятное поведение при отладке

## Решение проблемы cloud.google.com

### До исправления
```
15:28:22 - Начало сканирования cloud.google.com
[процесс завис навсегда]
```

### После исправления
```
15:28:22 - Начало сканирования cloud.google.com
15:29:22 - Timeout после 60 секунд (попытка 1/3)
15:29:24 - Retry попытка 2/3
15:30:24 - Timeout после 60 секунд (попытка 2/3)
15:30:26 - Retry попытка 3/3
15:31:26 - Timeout после 60 секунд (попытка 3/3)
15:31:26 - Источник помечен как failed, переход к следующему
```

## Конфигурация для разных сценариев

### Быстрое сканирование (для тестов)
```python
timeout=30       # Быстрый таймаут
max_retries=1    # Без retry
```

### Стандартное сканирование (по умолчанию)
```python
timeout=60       # Оптимальный баланс
max_retries=3    # Достаточно для надежности
```

### Медленные источники (специальный режим)
```python
timeout=120      # Долгий таймаут для больших страниц
max_retries=2    # Меньше retry чтобы не ждать слишком долго
```

## Мониторинг таймаутов

### Просмотр таймаутов в логах
```bash
# Все таймауты за сегодня
grep "tracking_timeout" logs/errors.jsonl | jq '.timeout_seconds' | sort | uniq -c

# Источники с таймаутами
grep "tracking_timeout" logs/errors.jsonl | jq '.url' | sort | uniq -c | sort -rn

# Средняя длительность успешных запросов
grep "change_tracking_source" logs/operations.jsonl | jq '.duration_seconds' | awk '{sum+=$1; count++} END {print sum/count}'
```

### Диагностика проблемных источников
```bash
# Источники которые всегда дают таймаут
grep -E "(tracking_timeout|changed_source_no_urls|unchanged_source_no_urls)" logs/errors.jsonl | \
  jq '.source_id' | sort | uniq -c | sort -rn | head -10
```

## Рекомендации

1. **Не уменьшайте главный таймаут ниже 45 секунд** - некоторые источники действительно медленные
2. **Всегда держите aiohttp timeout меньше asyncio timeout** - минимум на 5 секунд
3. **3 retry оптимально** - баланс между надежностью и скоростью
4. **Мониторьте таймауты** - если источник постоянно дает таймаут, проверьте его доступность

## Интеграция с последовательной обработкой (v4.0)

В версии 4.0 единая стратегия таймаутов интегрирована с последовательной обработкой:

```python
# change_tracking/monitor.py:532-700
async def scan_sources_sequential():
    for i, url in enumerate(sources, 1):
        log_operation(f'[{i}/{total}] 🔍 Scanning: {domain}')
        try:
            # Единый таймаут применяется к каждому источнику
            result = await asyncio.wait_for(
                scan_webpage(url),
                timeout=60
            )
            log_operation(f'[{i}/{total}] ✅ Completed: {domain}')
        except asyncio.TimeoutError:
            log_operation(f'[{i}/{total}] ⏱️ Timeout: {domain}')
        finally:
            # Гарантированное логирование прогресса
```

### Преимущества в v4.0:
- **Прогресс [1/50]** - видно какой источник обрабатывается
- **Изоляция таймаутов** - таймаут одного не влияет на другие
- **Простая отладка** - последовательное выполнение
- **Полное логирование** - каждый шаг записывается
